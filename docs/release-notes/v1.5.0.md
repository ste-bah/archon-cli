# Archon v1.5.0 — Topology, requirement traceability, and advisory lint

v1.5.0 gives Archon one representation for the graph it was already running.
Workflow specs, team runs and ordinary coding turns all produce the same shape,
and this release gives that shape a single IR, a single recording format, and a
single place where structural invariants are enforced. On top of it sit two new
read-only report surfaces — `archon requirements trace` and `archon workflow
lint` — and a learning loop that can now move a structural knob, not just
timeouts.

`/requirements` brings the slash primary count to 87. (The v1.4.0 notes said 85;
that was already wrong — `/world` shipped in v1.4.0 uncounted, so the real
v1.4.0 total was 86. `docs/reference/slash-commands.md` now says so.)

It also changes how hooks resolve a shell on Windows. **If you run Archon on
Windows, read the first section before upgrading.**

## Hooks now run under a POSIX shell on Windows — behaviour change

Hook commands and workflow verification each resolved a shell independently and
could disagree on the same machine. Hook execution asked only `which("sh")`;
Git for Windows adds `<git>\cmd` to PATH but not `<git>\bin`, so on a normal Git
install `which` found no `sh` and hooks fell through to whatever came next —
`cmd /C`, or, where the WSL launcher `C:\Windows\System32\bash.exe` is present,
inside WSL. Workflow verification on that same machine ran under Git's `sh.exe`.

Both now share one resolver, which finds Git's own `sh.exe` before considering
any `bash` and keeps `cmd /C` only for a machine with no POSIX shell at all.

**If you run Archon on Windows, check your hook commands.** A hook written in
`cmd` syntax — `%VAR%`, `dir`, backslash paths — that worked because hooks were
silently landing on `cmd` will now run under `sh` and break. Rewrite it in POSIX
syntax. Hooks on Linux and macOS are unaffected.

Hook subprocess execution is hardened alongside it: stdin is closed after the
payload is written, so a hook that reads to EOF no longer hangs until its
timeout.

## `archon requirements trace` — a proof ladder, not a coverage matrix

`archon requirements trace --prd <PATH> --tasks <DIR>` walks the requirement IDs
in a PRD to the code claiming to implement them, and reports what each link has
actually *earned*. Also `/requirements trace` in the TUI (alias `/reqs`).

Four ordered levels, and only the top two satisfy a promotion gate:

| Level | What earns it |
|---|---|
| `Unproven` | The fail-closed floor. No live anchor, or every anchor is stale. |
| `Candidate` | An anchor exists and its file still hashes to what was recorded. Cheap, and not proof. |
| `Exercised` | A verifier the task itself named ran and passed, **and** the ambient trace shows that run read the anchored file. |
| `Falsifiable` | Breaking the anchored code breaks the verifier. Planned always, executed only under `--falsify`. |

`Exercised` deliberately requires two independent facts, so evidence reused
across several requirements promotes only the ones whose anchored files that
command actually read. Every level below it carries a value naming the specific
missing fact rather than a bare failure.

- `--leann-db <PATH>` anchors against an existing LEANN code index and **never
  builds one**. Indexing holds the Cozo write lock across a whole
  `multi_transaction`, so a report that indexed would serialise every other
  writer for its duration. Without the flag every requirement reports
  `Unproven`, and the header says so in those words — "we did not look" is
  reported as such rather than as "no anchors found".
- `--falsify` closes the gap between "the verifier read this file" and "the
  verifier depends on this code" by experiment: it replaces the anchored lines
  with an abort, runs the verifier the task declared, and restores. The edge
  promotes only if the verifier failed while mutated. If it still passed, the
  edge was decoration and the report says so. **It mutates files in your working
  tree**, so it refuses on a dirty file, on unknown cleanliness, on a
  workspace-wide command, and on a verifier that did not pass on the original
  bytes — every refusal evaluated before a byte is written.

Exit status is success whichever way the report comes out. An unproven
requirement is a declared residual gap, not a failure; a traceability report
that failed CI would be muted within a week.

See [`archon requirements trace`](../reference/requirements-trace.md), including
the honest limit — `FileRead` evidence is file-granular, so a broad test that
reads a file without exercising the anchored function still promotes.

## `archon workflow lint` — four advisory analyses

`archon workflow lint` reads a task directory, a `WorkflowSpec` file or a
recorded graph and prints what four pure analyses found. Also `/workflow lint`.

- **Diamond conformance** — whether a fan-out reaches its reducer through
  independent verification: `UnverifiedFanout`, `SoleVerifier`, and
  `HomogeneousVerifiers` (several verifiers that all name the same agent, where
  the correlated failure survives every one of them).
- **Edge classification** — every `depends_on` edge split into `Dataflow`,
  `OrderingOnly` and `Unsupported`. `OrderingOnly` edges are listed under a
  heading saying they are explicitly *not* findings; reporting them as defects
  is what made an earlier version of this lint untrustworthy on a real corpus.
- **Stop-rule fusion** — where the parallel/sequential split disagrees with the
  dataflow, in both directions: coupling (nodes permitted to run at once where
  one reads what the other writes) and slack (an ordering that buys nothing).
- **Requirement coverage** — the tasks' `implements:` claims against the PRD's
  requirement IDs, implementing the Decomposition Completeness Gate.

**Nothing here can fail a run**, and that is a construction rather than a policy
that could be tightened later: the command never writes, never mutates a spec,
and exits success whether or not it found anything. Enforcement lives in the
guardrail admission layer, and the two do not share a code path.

Silence is distinguished from absence throughout. Two of the analyses stay
deliberately quiet on graphs declaring no dataflow, so the report says "no node
declares what it consumes, so no edge can be classified" rather than omitting
the section — *the lint looked and had nothing to work with* is a different fact
from *no findings*. Every finding carries a remedy naming the specific nodes.

See [`archon workflow lint`](../reference/workflow-lint.md) for which analyses
each of the three sources can support.

## The topology layer

Three layers, separated by what they are allowed to cost. Nothing on the hot
path may touch a database, and the fold that does never runs while work is in
flight.

- **The `TaskGraph` IR** (`crates/archon-topology/src/ir.rs`) is the common
  representation, carrying nodes with their role, `depends_on`, what they
  consume, write and read, a permission class and an optional fan-out spec. A
  `GraphOrigin` records which of the three producers built it — `Workflow`,
  `Team` or `Session` — and all team modes now route through it.
- **The ambient trace** appends one JSON object per line to
  `<project>/.archon/topology/<graph-id>/trace.jsonl`, alongside the declared
  `graph.json` when there was one. Ten record kinds cover node and agent
  lifecycle, tool attempts, file reads and writes, gates, verification and
  retries. `archon-topology` has no Cozo dependency at all, so "the hot path
  never touches a database" is enforced by the dependency graph rather than by
  review.
- **Guardrail admission** checks three structural invariants — agent cap, single
  writer, ungated irreversible — synchronously, in the same call stack about to
  execute the tool. A `Blocked` verdict returns before `tool.execute`, and the
  model receives an error for that attempt. Everything reachable from the
  callback is `DashMap` lookups; dominator computation and transitive
  reachability happen once when the graph is declared.

Supporting this, `archon-write-plan` is extracted as a leaf crate holding the
resource-key overlap table that live admission and the write coordinator both
answer from, and `ResourceKey::SharedAppend` lets several writers coordinate on
one append target instead of being treated as a conflict.

See [Topology](../architecture/topology.md), including where admission fails
open.

## `/workflow-prd` and `/workflow-prd-spec`

Two new built-in skills for the workflow path from a PRD to a running graph,
distinct from the existing `/to-prd` → `/prd-to-spec` skills chain and
deliberately not mixable with it inside one document.

- `/workflow-prd` writes `prds/PRD-<NAME>/PRD-<NAME>.md`.
- `/workflow-prd-spec` decomposes that PRD into
  `tasks/PRD-<NAME>/TASK-<DOMAIN>-<NNN>-<slug>.md`.

What the output feeds is the point: the task universe extractor reconciles
`depends_on` and `blocks` into one graph and refuses the run on any
contradiction, and both `archon workflow lint --tasks` and `archon requirements
trace` read the same directory. Use this path when you want the run itself to
stop on a cycle, an unresolved dependency, or a requirement no task claims.

The PRD and task templates are now machine-checkable, and unparseable task files
fail loudly instead of being skipped.

## SONA learns the four generated-workflow limits, and one structural knob

Four `[workflow.generated]` limits can now be learned per task class from
recorded run outcomes instead of being read verbatim from config:
`max_repair_iterations`, `max_investigation_iterations`,
`verification_branch_timeout_secs` and `host_call_timeout_secs`. Learning is
keyed per task class, so evidence from refactors does not move the budgets a
greenfield run gets.

Separately, `implementation_wave_fanout_width` — how many ready tasks the write
fan-out dispatches concurrently — is the first *structural* knob a learner may
propose. It is a disjoint type with a disjoint route key, so reading
`TunableGeneratedParameter` is enough to conclude that set can only move
timeouts and retry counts. Width is admissible where review-granularity and
verifier-count knobs are not, because the existing parallelism clamp means no
value the learner can produce creates concurrency the operator did not already
authorise — it can only ask for *less* than the configured cap. The proposal
still goes through the topology lints before it reaches a run, and the declared
dependency graph gets a veto.

**Both fail closed below five observations.** `MIN_OBSERVATIONS = 5`
(`crates/archon-pipeline/src/learning/sona/tuning.rs:57`) applies to the four
scalars and to the width knob alike. Under the threshold the tuner reports no
weight — `None`, not a weight of zero — and your configured value is applied
verbatim. There is no exploration term: an unproven weight is not a weight, so
the value is not nudged, sampled, or averaged toward anything. The same path is
taken when the learner rolled back on drift or produced a non-finite weight.

Above the gate there is no operator/learned blend either. A fully saturated
weight moves a value at most ±50% of what you configured, before floor and
ceiling clamp it, and the two timeout budgets only ratchet upward.

All of it is off unless you turn it on: tuning requires both `[learning.sona]
enabled` and `pipeline_recording`, and the latter defaults to `false`.

See [SONA workflow tuning](../operations/sona-workflow-tuning.md), including how
to find out why a particular run got a particular value.

## `ARCHON_DATA_DIR` now means one directory — behaviour change

`ARCHON_DATA_DIR` had two meanings: the memory resolver read it as the archon
directory, while session storage read it as that directory's *parent* and
appended `archon` itself. The defaults agreed, so nothing looked wrong until the
override was set — at which point the memory database landed at
`$ARCHON_DATA_DIR` and sessions at `$ARCHON_DATA_DIR/archon/sessions`.

It now means the archon directory everywhere, matching the memory resolver and
matching what `docs/reference/env-vars.md` already documented. **Default paths
are unchanged.** If you set `ARCHON_DATA_DIR` explicitly, your sessions move
from `$ARCHON_DATA_DIR/archon/sessions` to `$ARCHON_DATA_DIR/sessions`; move the
directory or drop the redundant level from the variable.

Nine tests that believed `XDG_DATA_HOME` isolated them were spawning children
against the real user database on Windows and macOS, where `dirs::data_dir()`
does not read it. They now set `ARCHON_DATA_DIR` too.

## Repository health

- The workflow subsystem is extracted into the `archon-workflow` crate: the task
  universe, generated contract and lifecycle, local host calls, artifact refs,
  completion credit, the dynamic source graph and the module target expansion
  all move out of the bin crate, and the `LlmClient` dependency is inverted
  behind a workflow port.
- The last production and test `include!` splice clusters become real modules.
- Adversarial review is per-task and the terminal reduce is narrowed; dead
  runtime, four inert spec fields and the unreachable reducers are deleted.
- Unguarded Cozo writes are routed through the `archon-cozo` write guard, and
  content-hash reservation is serialised on the database write lock.
- Files pushed over the 500-line ceiling by this branch are split, and the
  file-size scan no longer descends into `.claude/worktrees`.
- Several test defects that only reproduced on a developer machine are fixed: a
  mock-server timeout presenting as six env-isolation failures, three
  unserialised-state defects, and cold PowerShell output fixture startup.
