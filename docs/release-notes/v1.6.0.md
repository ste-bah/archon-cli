# v1.6.0

A feature release. Agents can now hand work and findings to each other through a
durable task board, check their own edits against the repo's own gates, and be
watched from the browser while they do it.

The through-line is narrower than "multi-agent support": every part of this
release exists because something was happening that nobody could see.

## The agent task board

Until now a subagent that noticed something outside its assignment had exactly
one place to put it: its final message. The parent then summarised several such
messages into a paragraph, and the finding was gone. "Rate limiting added to the
LLM client" is what you read; "three of four providers wired" is what happened.

`board_items` is a dedicated relation in the memory graph's database. Not a
`MemoryType`, and the reasons are concrete rather than stylistic. Memories have a
fixed twelve-column schema, so board state would have to be encoded as tags —
against a ceiling of sixteen non-trend tags asserted in Datalog, not merely in
Rust. `update_memory` replaces the whole tag vector last-writer-wins with no
compare-and-set, so two agents claiming one item would silently lose a claim. A
type-only filter is a full relation scan, and a board is polled by everything
that looks for work. And there is precedent: `PersonalitySnapshot` serialised
JSON into a memory's `content` field and needed filters added at three separate
read paths afterwards to keep it out of ordinary recall.

**Claims are atomic.** The compare-and-set states its precondition twice — once
in the `%if` that decides whether the write block runs, once in the rule body
that decides which rows it touches — so a mistake in either alone cannot produce
a write that ignores prior state. Whether the claim succeeded is returned from
inside the transaction that decided it, never from a preflight read, and the
loser gets the authoritative row so it can see who holds the item rather than
merely being refused.

**Board items are never pruned.** The memory garden does not know the relation
exists. A handoff that quietly decays after thirty days is worse than no handoff,
and the test for this runs consolidation with deliberately destructive settings —
staleness zero days, importance floor above any real value, a one-memory cap —
then asserts the memory count actually fell, so the garden provably ran, and that
the board row is untouched.

See [`docs/architecture/agent-task-board.md`](../architecture/agent-task-board.md),
which is explicit about what is not built yet.

## A third review verdict, and a run that cannot end with open issues

Adversarial review was two-valued: needs-remediation, or accepted. An agent that
discovered its assignment could not or should not be done as written had nowhere
to put that, and the only move left was to produce something that passes. The
incentive is exactly backwards — it teaches an agent to satisfy the reviewer
rather than report the problem.

`assignment_invalid` is the third verdict. It terminates the loop for that
assignment instead of sending it round for remediation. The obvious risk is that
it becomes a way out of hard work, so admission is structural rather than
persuasive: the claim must carry the host-stamped review branch id — a field no
model writes — plus a named task, a stated reason, and `file:line` evidence. A
claim that fails any of those is **downgraded to ordinary remediable work**, not
discarded, so a badly-formed report still gets acted on.

The drain gate is the other half. A run cannot report success while board items
are still open: every one must reach `resolved`, `promoted`, or `declined` with a
recorded reason. `escalated` deliberately does not count — an escalation is an
unanswered question, and letting it pass ships a question as an answer.

The gate runs at the last barrier and is the only board read in the run.
Reading the board inside a fan-out would make a replay non-reproducible, which
matters more than the extra round trip saves.

One limit, stated rather than left to be discovered: this runs in the decomposed
V2 lifecycle. The v3 script lifecycle is the default and never constructs a
`LifecycleDriver`, so neither the gate nor the third verdict executes there yet.

## Subagent identity

A tool executing inside a subagent could not tell which subagent it was.
`ToolContext` carried the *parent's* session id and nothing else identifying, so
anything a subagent wrote had no attributable author — and a claim that cannot
name its holder cannot be released when that holder dies.

`ToolContext` now carries `subagent_id`, stamped from the same id the subagent is
registered under, so a board write and a liveness check agree on who is who. The
parent's session id stays alongside it: they answer different questions, and
collapsing them is how the ambiguity arose.

The same gap existed in hooks. `HookContext` has always had an `agent_id` field
that nothing populated, so an in-process `SubagentStop` callback fired correctly
and could not tell which subagent had stopped.

## A claim lasts as long as its holder

Claims have no TTL. A claim is valid while the agent holding it is still
executing, and a timeout would only trade one wrong answer for another: too
short releases work in progress, too long parks the board after a crash.

Getting that right needed liveness to be a single question. It was not. It was
answered by asking `TASK_MANAGER` and then `BACKGROUND_AGENTS`, because
`TaskCreate` and `AgentTool` happened to record their agents in different
places — and `archon-pipeline` recorded in neither, so its agents read as dead
from birth and the sweep released their claims **while they were still
working**. That is the precise double-work the lease exists to prevent, and it
failed silently: nothing errors, the claim is simply handed to someone else.

Adding a third arm would have fixed the report and kept the shape that caused
it, so the registration moved instead to the one function every runner passes
through. Liveness is now a property of having been spawned, the lookup is one
lookup, and the next spawn path is covered without anyone remembering to.

Two details make it hold. The registration is released when the **runner** ends
rather than when the call returns — different moments on the auto-background
arm, where the agent keeps working past the return and `SubagentStop` never
fires, so nothing hook-based could be trusted with it. And the resume path
reuses an agent's original id, so registering can meet an entry that is already
there; a resumed agent inheriting its predecessor's terminal status would have
read as dead for the whole of its second life, decided by whether a 60-second
reaper happened to run in between.

One visible consequence: agents spawned by `SendMessage` are registered now, so
they appear in the dashboard's agent panel where they previously did not.

## Self-checking edits

Every regression in a long session was found by a human and reported back as a
complaint, never noticed by the agent that caused it. In one session the agent
pushed a file past the repo's own 500-line gate, left two more over it, and
noticed none of them — while the rule sat in `scripts/check-file-sizes.sh` the
whole time.

The feedback channel already existed and nobody had used it: a `PostToolUse`
hook's `additional_context` is appended to the tool result and enters the
transcript, so the model reads it on its next turn. It is the only event with
that property. What was missing was one fact — the payload never said which file
had been edited, though the value was in scope at the call site.

`scripts/self-check-file.sh` now applies the line limit and the allowlist to that
one file. Silence is a pass, so a clean edit costs no transcript budget. It
deliberately does not invoke `check-file-sizes.sh`, which walks over three
thousand files and takes roughly 165 seconds; a single file costs about 0.4
seconds, nearly all of it shell startup.

Two things only surfaced under test. The hook registry deduplicates by
`(type, command)` and keeps the last, so three entries sharing a command string
collapse into one — the obvious config would have silently checked only
`NotebookEdit`. And `.archon/` was ignored wholesale, which makes a negation for
a file beneath it unreachable, so the shipped config would have been invisible to
CI and to every other clone.

## `/web` — a dashboard for the session you are actually in

`archon web` has always started a dashboard, and it has always been unable to
answer the one question worth asking of a running session: what are the agents
doing right now? Not for want of an endpoint. `BACKGROUND_AGENTS` holds live
`JoinHandle`s and `CancellationToken`s, which do not cross a process boundary at
any price, so a separate `archon web` process could never report live agents
regardless of what was recorded for it.

`/web` starts the same server **inside** the TUI process. That is the whole
mechanism, and `archon web` standalone is unchanged for anyone using it to browse
memory and corpora.

Attached mode differs from standalone in two deliberate ways:

- **The agent panel is populated.** `/api/agents/live` reports the agents this
  process spawned, which now means every spawn path (see the liveness section
  above). Tasks are listed in their own right, since a task has a description and
  a creation time that a bare subagent id does not.
- **The chat tab is not constructed.** Running a second independent conversation
  beside the one you are watching is worse than having no chat at all — two
  histories, one session, and no indication which one you are reading.

Live updates are streamed rather than polled. `EventSource` was deliberately not
used: it cannot set an `Authorization` header, and the server refuses
query-string tokens, so it would work on localhost and fail 401 on any
non-loopback bind — the kind of bug that only appears in someone else's
deployment. The existing fetch-based SSE reader carries the header properly.
Snapshot surfaces that are state rather than events, the agent panel among them,
are still polled: streaming a snapshot means either diffing it or resending the
world on every change.

`/web` takes an optional port, and `/web status` and `/web stop` do what they
say. The dashboard also stops when the session ends. Expect the event feed to
look sparse for now — only a handful of `record()` call sites exist, all in web
chat and ingest; the agent panel carries the useful signal today.

## Consolidation no longer reports "unavailable" as "clean"

CozoDB is single-writer, so the first archon process owns the database and any
subsequent one is a client. Which mode a process gets is decided by a startup
race, not by configuration.

`embedding_neighbours` was the one memory operation missing from the RPC surface,
so a second instance received an empty result — and the semantic dedup pass read
that as "no duplicates found". A TUI that happened to start second therefore
skipped the entire semantic pass, merge band and review band both, and reported
zero, which is indistinguishable from a tidy store.

The type now carries the distinction: `None` means the store has no vector
search, `Some(vec![])` means the search ran and found nothing. A caller cannot
read one as the other without doing so deliberately. And the gap itself is
closed — a remote store gets real neighbours over RPC, verified by a round trip
that compares ids and distances against the same query run locally.

## Hooks documentation

`docs/reference/hooks.md` is new, and replaces a page that was wrong rather than
merely out of date: it documented a TOML shape, a `blocking` field, `path_regex`
matchers, and a `/hooks add` subcommand that do not exist. Someone following it
would have written a config that silently never ran.

The useful part is the table of what the runtime actually does with each event's
result, because that is the only way to choose an event correctly. It also
records that `matcher` is parsed, hashed into the hook id, shown by
`/hooks list`, and never applied at execution — and that `async_rewake`,
`status_message` and `permission_behavior: "ask"` are declared and not wired.

## Upgrading

Nothing to do. The `board_items` relation is created idempotently on first use,
so existing stores need no migration, and the self-check hook ships enabled with
a five-second timeout and a failure policy that cannot block a turn.
