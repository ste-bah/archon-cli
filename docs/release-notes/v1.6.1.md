# v1.6.1

A patch release. It finishes the web workbench that v1.6.0 started — the
browser is now a full Archon surface rather than an inspector beside one — and
fixes three things that were broken outright, one of which stopped document
ingest working at all.

Nothing here changes an existing default. Both new surfaces ship off.

## Document ingest was crashing

`archon docs ingest <path>` aborted before reading a byte of the document:

```text
thread 'main' panicked at tokio-1.52.3/src/runtime/blocking/shutdown.rs:51:
Cannot drop a runtime in a context where blocking is not allowed.
This happens when a runtime is dropped from within an asynchronous context.
```

`reqwest::blocking` creates and owns a private Tokio runtime, and constructing
one from inside another runtime's context is documented misuse. Every caller of
`init_embedding` reaches it from `#[tokio::main]` — `docs ingest`, `docs index`,
`kb`, `reprocess`, `vector-migrate` and the web chat bridge are all inside the
runtime — so with an OpenAI-compatible embedding provider configured, ingest
exited 101 on the CLI and through the web alike.

The client is now built on a plain `std::thread`, which has no runtime context,
and requests hop off the runtime the same way so a provider that constructs
cleanly does not then fail on first use. Where there is no runtime — the
indexing hot path — nothing changes.

## The TUI crashed on short terminals

Opening the TUI in a terminal shorter than about 22 rows killed the process on
its first frame with `index outside of buffer`. The splash lays out a fixed
composition at absolute offsets and never compared them to the available
height; past the bottom of the buffer, ratatui panics rather than clipping.

A short terminal now loses the bottom of the splash, which is decoration, and
keeps the top, which names the version and the working directory. A tiled
window manager, a split pane, or any terminal window under roughly 400px high
reproduced this — it is not specific to the new terminal pane, which is merely
where it was found.

## Terminal pane in the web workbench

The workbench spawns `archon` under a pseudo-terminal and streams it to
xterm.js over a WebSocket. Because it is terminal emulation rather than a
reimplementation, everything the TUI can do works there — slash commands,
permission prompts, `/model`, `/agents` — and it needs no upkeep as the TUI
changes. Dropping a file on the pane uploads it and types `@<path>` at the
prompt, which is the TUI's own attachment convention.

It is a **new** session, not the one you launched the workbench from: Archon
does not own the terminal it was started in, so there is no existing stream to
join. Closing the tab kills the process.

Two hard requirements, neither of them a default:

- **Loopback only, unconditionally.** A non-loopback bind removes the route
  outright, including under
  `unsafe_allow_unauthenticated_nonlocal_bind_for_cli` — that flag exists to
  put a read-only workbench on a trusted network and must not silently become
  remote code execution.
- **Its own policy flag**, `policy.web.allow_web_terminal`, never
  `allow_mutating_actions`. Ingesting a document and running arbitrary commands
  are not the same risk.

When either says no the route is not registered at all and the path 404s,
rather than a handler returning 403. A shell should not look like something one
flag away from being unlocked.

## Knowledge-store controls

The Ingest tab could show the state of the stores but not act on it. It now
carries the operations where a browser genuinely beats a command line:

- **Upload** — a file picker and drop zone. Ingest always took a path, which is
  fine when the file is on the machine running Archon and tedious when it is on
  the machine running the browser. This *produces* a path rather than being a
  second ingest route.
- **Delete** — permanent removal of a document and everything derived from it,
  with a confirmation that names the chunk, page and artifact counts. Behind
  its own flag, `policy.web.allow_document_deletion`, deliberately not implied
  by `allow_file_uploads`: wanting drag-and-drop is not asking for a delete
  button on every row.
- **Index controls** — pause, resume, cancel and retry-failed. The queue
  counters were already on the page with no way to move them. Pause and cancel
  also release the job's leases, since a leased chunk whose owner has stopped is
  otherwise stranded: neither pending nor indexed.

Three panels were also fetching real data and rendering none of it — pipeline
definitions, artifact roots and recent sessions; the document store path
probes; the log and budget locations. On a project where nothing had run yet,
the Pipelines tab was blank despite knowing exactly which pipelines were
configured.

## Git's shell is found on Windows (#118)

Shell discovery derived Git's install root by stripping a fixed two components
from the `git.exe` it found. `where git` returns a different layout depending on
the calling shell — `<root>\cmd\git.exe` from PowerShell and cmd, but
`<root>\mingw64\bin\git.exe` first from Git Bash — so from Git Bash the
derivation produced `<root>\mingw64\bin\bash.exe`, which does not exist. The
fallback was a bare `bash`, which on Windows resolves to the WSL launcher: it
runs inside the Linux filesystem, cannot see `F:\...` at all, and reports "No
such file or directory" for a perfectly valid Windows path.

Discovery now walks every ancestor of every candidate and takes the first
`bash.exe` that exists, and never selects the WSL launcher. The symptom was a
suite that passed when invoked from PowerShell and failed from Git Bash, with
an error naming a file that was plainly there.

## Setup scripts

`~/.archon-marker-venv` is the path Archon probes for a RapidOCR interpreter,
and no installer created it. What the scripts printed instead —
`python3 -m pip install rapidocr opencv-python` — is refused by Debian 12+,
Ubuntu 23.04+, Fedora 38+, Arch and Homebrew under PEP 668, so the advice could
not work on any current distro.

Both installers now take a flag (`--with-ocr`, `-WithOcr`) that creates the
virtualenv at exactly that path and installs into it. The probe itself was also
Unix-only: a virtualenv puts its interpreter in `Scripts\python.exe` on Windows
and `bin/python` elsewhere, so on Windows it could never fire however the venv
had been created.

## Documentation

`docs/operations/web-workbench.md` now has a screenshot and a description for
every one of the fifteen tabs, in sidebar order, including the five it had
never covered.

`docs/architecture/agent-task-board.md` lost a section headed "What is not
built" whose first sentence was "Nothing structural", and another called "What
used to be here". The mechanism they described is now documented as behaviour,
and the document opens with what an agent actually does with the board rather
than with storage rationale.

## Upgrade notes

Nothing is required. Both new surfaces are off by default and need explicit
policy:

```toml
[policy.web]
allow_web_terminal = true          # browser terminal pane; loopback only
allow_mutating_actions = true      # required by everything below
allow_file_uploads = true          # upload and drag-drop
allow_document_deletion = true     # delete button on documents
```

The v1.6.0 upgrade notes still apply: the repository code index does not build
at session start (`[code_index] index_on_startup = true` restores it), and
Intel macOS is no longer built.
